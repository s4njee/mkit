# E2.8 text input evidence

Status: four chapters are published under `book/src/text-input/` using five compiling anchors from `examples/text_input`. The workspace pins `gpui-pre = 0.3.5` at Zed commit [`d89e9c2124b2786a390c7a451c7488601b4da2e1`](https://github.com/zed-industries/zed/tree/d89e9c2124b2786a390c7a451c7488601b4da2e1). Earlier locked package tests, Clippy, four macOS screenshot comparisons, book checker, and mdBook build passed. The field measures input ranges with the same pinned GPUI `WindowTextSystem::shape_line` API and text style it paints. TestWindow uses `NoopTextSystem`, so it can verify UTF-16 range conversion and origin math but cannot distinguish normal glyph advances; the macOS HeadlessSession check uses the platform text system for narrow/wide glyph and surrogate-pair assertions. Native OS IME candidate-window placement remains untested.

## Review boundaries and upstream reports

- [Zed issue #42774](https://github.com/zed-industries/zed/issues/42774) requests a complete GPUI single-line input component, including keys, pointer interaction, cursor blink, and cross-platform IME. It is a feature request in a later revision, not proof that this pin lacks every individual API.
- [Zed issue #62661](https://github.com/zed-industries/zed/issues/62661) reports macOS composition missing in a nonactivating panel on a later GPUI revision. It does not establish a defect in this field or pin.
- [Zed issue #46055](https://github.com/zed-industries/zed/issues/46055) reports a misplaced candidate window in a narrow macOS terminal/CLI case. Use it to motivate manual candidate-position checks, not as proof of a general GPUI bug.
- [Zed issue #42794](https://github.com/zed-industries/zed/issues/42794) reports an off-by-one caret position after selection on Windows in a later Zed editor. It is a test prompt, not a diagnosed UTF-16 conversion bug.

Ask a maintainer to review the public field API, keyboard and accessibility behavior, undo policy, visual baselines, and book accuracy. The example is deliberately narrow: no pointer caret placement, grapheme-aware movement, Shift+Arrow extension, native IME candidate-window validation, or full accessibility contract. The selected and marked screenshot states are synthetic fixtures. Candidate geometry is API-level evidence from GPUI's text shaper; native OS placement still needs a manual input-method check.

## Native IME verification record

The [chapter's manual procedure](src/text-input/ime-composition.md#verify-a-native-input-method) asks for a real desktop session, Japanese composition after non-BMP text, candidate positioning before and after moving the window, commit and cancel/unmark outcomes, and a screenshot or recording of the actual OS candidate UI. Log OS/version, input method/language, display scale, and display arrangement so a misplaced panel can be reproduced. Repeat with Chinese and Korean input methods where the app promises them. No native IME run or candidate-window capture has been recorded for E2.8 yet; the corresponding `plan.md` checkbox remains open.
