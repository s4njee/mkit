# E4.6 — State patterns foundation

`mkit_core::state::ComponentState<T>` gives a stateful component one consistent
way to distinguish locally owned values from parent-controlled values.
`request_change` returns a typed `StateChange<T>` containing the previous value,
the requested value, and the ownership mode. It commits the value in
uncontrolled mode. In controlled mode it leaves the current value intact until
the owner supplies the next value with `set_value`.

## Using it from a GPUI entity

A component stores `ComponentState<T>` as a field on its GPUI `Entity<T>` model.
When an interaction requests a change, the component calls
`let change = self.value.request_change(next);`, emits a component-specific
event carrying `change` with `cx.emit(...)`, then calls `cx.notify()` if its
rendered state changed. An uncontrolled state has already changed before the
event is emitted. A controlled state emits the proposal and continues rendering
the old value; its parent handles the event and updates the entity with
`set_value` when the new controlled value arrives.

The core intentionally does not implement `gpui_pre::EventEmitter` for
`ComponentState<T>` or a generic event. In pinned GPUI Pre 0.3.5,
`Context::emit` requires the *emitting entity type* to implement
`EventEmitter<Evt>`. A helper value cannot satisfy that requirement on behalf
of the entity. Each component must declare its semantic event, implement the
marker trait on its entity type, and emit through its own `Context<T>`. For
example, a selection widget can define `SelectionChanged(StateChange<usize>)`
and implement `EventEmitter<SelectionChanged>` for its entity type.

## Event and update contract

- `StateChange::previous()` is the value just before the interaction.
- `StateChange::value()` is the requested value. It is a proposal in controlled
  mode and the newly committed value in uncontrolled mode.
- A payload is returned for every request, even if the requested value compares
  equal to the current value. This avoids requiring `PartialEq` and leaves
  duplicate suppression to the widget's event contract.
- `ComponentState::set_value` models either a new controlled prop or an explicit
  reset in uncontrolled mode. It does not create a `StateChange`; owner-driven
  synchronization is not a user request.
- Emitting a typed event does not notify GPUI observers. A component that
  changes its rendered state must call `cx.notify()` separately.

## Current scope and gaps

This is a small value-state helper, not a replacement for GPUI `Entity<T>` and
not a derive or trait that components must implement. The helper does not
perform equality checks, event emission, entity notification, event naming,
subscription management, or parent/child prop wiring; these stay with each
component.

The Part II [controlled-state chapter](../book/src/state/controlled-state.md)
includes a compiling anchor from `examples/state_entities/src/component_state.rs`.
That example renders an uncontrolled and a controlled toggle, subscribes to
their typed `ToggleChangeRequested` events, and has a parent accept the
controlled proposal. Four library tests in the example crate pass. Its
`component_state_screenshot` target compares light, dark, and high-contrast
macOS Metal headless captures at 640 × 400 logical pixels and scale 1, plus
light at scale 2. All four baselines were inspected after generation and the
comparison passes. The sample's clickable controls are
pointer-only teaching UI, not conformant registry toggle components; it does
not establish keyboard or accessibility behavior. Public API naming and book
accuracy need maintainer review under the project working agreement.
