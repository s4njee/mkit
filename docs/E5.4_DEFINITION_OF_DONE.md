# E5.4 — Component definition of done

This applies to every source component in `registry/`. A component may be
implemented before every item is complete, but it is not marked complete in
`plan.md` or advertised as conformant until the whole list passes. The
component pull request links the evidence; the machine checks catch missing
artifacts and failing tests, while a maintainer decides the contracts and
visible quality.

## Contract review

- A maintainer approves the component spec, public names and props, typed event
  contract, controlled and uncontrolled behavior when applicable, keyboard
  map, and accessibility role and properties. The spec records unresolved
  questions before implementation.
- The spec cites a WAI-ARIA Authoring Practices pattern or a documented
  platform convention. Deviations are explicit. Every shortcut uses a GPUI
  key context and action so applications can rebind it.
- The implementation reads colors and design values from the mkit theme
  `Global`. Fixed sizes are tokens or justified in the spec. Registry source
  depends only on GPUI and `mkit-core` unless its approved spec says otherwise.

## Conformance evidence

- Generated keyboard cases pass for each specified key in each applicable
  state. Custom interaction tests cover behavior the front block cannot
  express, including pointer and IME behavior where relevant.
- A normalized accessibility snapshot matches each state on a platform whose
  adapter is active. The snapshot and any diff are inspected. Until the
  headless adapter can be activated, an inactive-tree result is a documented
  gap, not a passing snapshot; a native inspector check is recorded separately.
- Screenshot baselines compare every declared state in light, dark and high
  contrast at 1× and 2× scale on a supported renderer. The maintainer inspects
  new baselines and diffs. Platforms without a headless pixel renderer are
  listed as unverified.
- The component's custom and generated tests, relevant workspace build,
  strict Clippy, formatting, book build, and GPUI Kit coexistence build pass.

## Product integration

- A docs page has at least three compiling example usages, a keyboard table,
  and harness screenshots. Code is included from example crates rather than
  copied into the book. A maintainer reviews the explanation for accuracy.
- `cargo mkit add` installs the source and dependency closure; the component is
  also exposed through the `mkit` crate. Both installation paths build.
- The gallery presents every state and every theme. Its states have stable
  selectors or IDs for inspection and screenshot capture.

## CI and review boundary

CI validates the machine-readable spec and registry, generated suite
freshness, both complete pilot keyboard maps, the supported overlay screenshot
smoke case, workspace build, tests, strict Clippy, formatting, book, and GPUI
Kit coexistence sample. The
`scripts/check_e5_dod.py` guard keeps the PR checklist and these wired CI
commands from silently drifting apart. It checks process wiring only; a green
guard does not mean any component has passed its checklist.

The PR template requires a maintainer to record decisions and link evidence
for each component. CI cannot approve API names, keyboard conventions,
accessibility meaning, or visual baselines. Current platform gaps include
inactive accessibility in the pinned headless test window and the absence of
a full state × theme × scale screenshot matrix for every component. Such cases
must remain pending and documented until supported evidence exists. A missing
platform capability stays open in the component's spec and plan; it is not
converted into a pass. E5.4 process enforcement does not complete E5.3 or mark
any component conformant.
