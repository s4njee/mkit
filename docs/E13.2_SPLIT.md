# E13.2 pro-app visual parity — proposed story split

Planning only. E13.2 is `P3`, `XL`, and depends on E13.1. [plan.md](../plan.md) requires a split
before work starts. These slices bring the thirteen E8 components to the visual language the
everyday components adopted in E7.1–E7.7 and E13.1. Each slice is small enough to restyle, inspect,
and review on its own. The decisions below are proposals for maintainer review.

## Shared approach

Reuse the everyday restyle rules recorded in each restyled component's spec "Theme" section (for
example `registry/button/spec.md` and `registry/tabs/spec.md`):

- Theme tokens only, with a local colour-mix helper for the shadcn "muted", "accent", "input" and
  "border" roles. Light and dark are told apart by background luminance through
  `mkit_core::contrast`. High contrast is detected by theme name and keeps solid, strong outlines.
- Opaque fills under shadows (GPUI fills inside a shadow). Disabled colours are mixed 50% over the
  background instead of using GPUI opacity.
- Keyboard focus is a focus-coloured border plus a 3px ring at 50% alpha. Every matrix gains a
  focused state where the fixture can focus deterministically.
- Icons, handles and glyph-like marks are vector paths, never text glyphs.
- Behaviour, public API, events, keyboard contracts and accessibility trees stay unchanged. API
  gaps found along the way go to E13.3, not into these slices.

Pro apps are denser than the web previews. E9.1 calls for a dense, dark-first default, so each
slice keeps the component's existing control heights unless the maintainer approves the shadcn
sizes (see open questions). Colours, borders, radii, shadows, focus and hover follow the everyday
components either way.

Every slice updates spec Theme sections first, then code, then the component's own screenshot
matrix and book images (inspected in light, dark and high contrast at 1× and 2×), then reports
knock-on changes in the E8 gallery scenes and the Laika adoption branch. The E8 gallery scenes are
refreshed once per slice, after inspection.

## P1 — Numeric inputs

**Scope.** Scrubbable number field and precision slider. Both build on looks that already exist:
the restyled TextField (field chrome, focus ring, invalid state) and the restyled Slider (track,
range fill, thumb). Add the scrub affordance (cursor hint and drag feedback) and the bipolar
centre mark as vector drawing.

**Acceptance.** Fields and sliders are indistinguishable in chrome from TextField and Slider at the
same size. Scrub, fine-drag and reset states are visible in the matrix. Number field IME and
selection rendering stay correct in all themes.

**Evidence.** Existing number-field (36) and precision-slider (30) matrices regenerated and
inspected; keyboard conformance; the E8.2 pilot's generated suites still pass.

## P2 — Graph editors

**Scope.** Curve editor, gradient editor, colour tools, histogram. Restyle the plot surfaces: grid
lines in the border role, axes and labels in muted text, points and stops as filled handles with a
background ring and shadow (the Slider thumb look), selected handles with a focus ring, and panel
chrome as bordered rounded-lg cards. Colour content (curves per channel, gradient stops, wheel
hues, histogram channels) stays data-driven and is not re-tokenised.

**Acceptance.** Handles read clearly on every theme without relying on colour alone. Selected and
focused handles differ. Histogram clipping indicators remain visible in high contrast.

**Evidence.** Curve (30), gradient (30), colour tools (18) and histogram (24) matrices regenerated
and inspected; keyboard conformance where adapters exist.

## P3 — Panels and lists

**Scope.** Property inspector, layer panel, command palette, shortcut editor. Rows adopt the
restyled Sidebar/Tree row look (radius-sm rows, accent fill for selection, ghost hover, vector
chevrons). Group headers use the restyled Disclosure. The command palette adopts the restyled
popover surface and list rows; the shortcut editor adopts restyled rows and keycap KeyHints.

**Gate.** The command palette and shortcut editor baselines are still waiting on maintainer
acceptance of the KeyHint change (see [review queue](REVIEW_QUEUE.md)). Accept or reject those first
so this slice compares against agreed baselines.

**Acceptance.** Mixed-value and reset-to-default states stay distinguishable in the inspector.
Visibility and lock toggles in the layer panel read as buttons, not decoration. Conflicts in the
shortcut editor use the danger role with a text cue.

**Evidence.** Inspector (30), layer panel (30), command palette (12) and shortcut editor (36)
matrices regenerated and inspected.

## P4 — Canvases

**Scope.** Viewport chrome (rulers, guides, zoom controls), timeline (tracks, clips, ruler, playhead,
keyframe markers), node editor (nodes, ports, wires, box selection, minimap). Nodes and clips become
bordered rounded surfaces with the card shadow; selection uses the focus ring; ports, markers and
the playhead are vector handles; rulers use muted text and border-role ticks.

**Acceptance.** Dense timelines and node graphs keep labels readable and hit targets unchanged.
Selection, hover and focus remain distinct at high zoom. Wire colours stay data-driven.

**Evidence.** Viewport (24), timeline (48 plus the T3/T4 book images still waiting on review) and
node editor (78) matrices regenerated and inspected.

## Suggested order

P1 first (smallest, reuses finished looks), then P3 once its gate clears, then P2 and P4, which
carry the most custom drawing. P2 and P4 can run in parallel.

## Open questions

- Should pro components adopt shadcn's control heights (36px default) or keep today's denser
  heights under the E9.1 dark-first, dense principle? Colours and chrome follow the everyday look
  either way.
- Should graph and canvas handles share one size token across components (for example a single
  "handle" size), which would be new theme API and needs approval?
- Should chart-like content (histogram, curves) wait for E13.5 charts so axes and grid styling are
  shared, or be restyled now and aligned later?
- Laika adopts Histogram, Slider and SegmentedControl on a branch. Should Laika's baselines move
  with each slice, or only when the adoption branch is merged?
