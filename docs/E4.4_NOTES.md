# E4.4 — Motion foundation

`mkit_core::motion` maps common component transitions to the theme's duration
tokens. Hover and press use `Theme.motion.fast_ms`; open and close use
`Theme.motion.normal_ms`. A zero token disables that transition. Callers can
use `transition_duration(theme, kind, app.reduce_motion())` when they need a
duration, or `transition_animation(theme, kind)` with GPUI's
`AnimationExt::with_animation`.

## Reduced motion contract

GPUI Pre 0.3.5 exposes `App::reduce_motion()` and `App::set_reduce_motion()`.
Its `AnimationExt::with_animation` wrapper checks this flag, renders a static
state when enabled, and schedules no animation frames. E4.4 adds platform
adapters that synchronize supported OS settings to this flag while the
returned monitor guard is retained by the host application. Dropping the guard
sends a stop message; the monitor task then releases its OS observer.
Unsupported platforms report no OS value and leave the app-level preference
under application control.

The adapter reports its scope explicitly. macOS reads AppKit's
`NSWorkspace.accessibilityDisplayShouldReduceMotion`; runtime changes are
detected through `NSWorkspaceAccessibilityDisplayOptionsDidChangeNotification`.
Windows reads `UISettings.AnimationsEnabled` and maps disabled system UI
animations to GPUI reduced motion; it listens to
`UISettings.AnimationsEnabledChanged`. This is a system animation signal, not a
claim that Windows exposes a separate reduced-motion preference through this
API. Other platforms, including Linux, have no bridge in this increment and
must configure `App::set_reduce_motion` themselves. The bridge does not change
system settings.

Linux intentionally remains unsupported. GNOME GTK exposes
`gtk-enable-animations` and `gtk-interface-reduced-motion` as separate
settings, so mapping the older global animation toggle would not accurately
represent the accessibility preference. See the [GTK Settings API](https://gnome.pages.gitlab.gnome.org/gtk/gtk4/class.Settings.html).

## Motion helper scope and checks

The transition helpers do not choose easing curves, interpolate component
properties, or impose animation on components. Components still choose which
properties to animate and what their start/end values mean. Tests cover token
mapping, reduced-motion duration selection, high-contrast zero durations,
GPUI `Animation` construction, and the platform preference synchronization
contract. The headless test feeds preference-change notifications through the
GPUI monitor loop and checks both enabled and disabled states, plus guard-drop
cleanup. Host `cargo test -p mkit-core --locked` and
`cargo clippy -p mkit-core --all-targets --locked -- -D warnings` pass with
this implementation. `cargo check -p mkit-core --locked --target
x86_64-unknown-linux-gnu` also passes. Windows target checks were attempted for
`x86_64-pc-windows-gnu` and `x86_64-pc-windows-msvc`. The GNU build stopped
because this host lacks `x86_64-w64-mingw32-windres`. For MSVC, Homebrew's
`llvm-rc` was found and used, but GPUI Pre's resource script then failed to
resolve its relative `gpui.manifest.xml` include. Neither attempt reached
mkit-core's Windows adapter. A standalone `cargo check --offline --target
x86_64-pc-windows-msvc` probe using the same pinned `windows = 0.62.2` and
`futures = 0.3.34` bindings compiled the Windows preference reader, event
handler, and event unregistration code. This validates those API signatures,
not the full mkit-core target or native runtime behavior. Native macOS/Windows
preference changes still need manual validation; harness screenshots remain
pending. Public API and token naming need maintainer review.
