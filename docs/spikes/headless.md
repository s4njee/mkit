# E1.1: GPUI headless harness spike

Status: source investigation and local macOS fixtures run; other operating systems and machines remain untested. This page applies to the workspace's exact `gpui-pre = 0.3.5` pin. The package identifies its upstream Zed revision as `d89e9c2124b2786a390c7a451c7488601b4da2e1` in its published `Cargo.toml`; conclusions below are based on the published `gpui-pre` and `gpui-pre-platform` 0.3.5 source, not a newer GPUI release.

## Construction and capture

`HeadlessAppContext::new(text_system)` constructs a `TestPlatform` without a renderer. `HeadlessAppContext::with_platform(text_system, assets, renderer_factory)` accepts a `PlatformHeadlessRenderer` factory; `open_window` creates a hidden window, and `capture_screenshot` calls `Window::render_to_image` and returns an `image::RgbaImage`. Without a renderer, the test window returns `render_to_image not available: no HeadlessRenderer configured`. A local Metal capture succeeded with the supplied renderer factory.

The convenience factory `gpui_platform::current_headless_renderer()` (from package `gpui-pre-platform`) returns `MetalHeadlessRenderer` on macOS and `None` on every other target in this version. Accordingly, the provided factory uses Metal on macOS. Windows and Linux headless screenshots are **unsupported by this factory**; a custom renderer implementation would be needed. No Windows or Linux capture has been run for this spike. Other GPUI rendering paths do not establish a headless screenshot capability.

Sources: `gpui-pre-0.3.5/src/app/headless_app_context.rs` (`new`, `with_platform`, `open_window`, `capture_screenshot`); `gpui-pre-0.3.5/src/platform/test/window.rs` (`render_to_image`); `gpui-pre-platform-0.3.5/src/gpui_platform.rs` (`current_headless_renderer`, lines 83–99); `gpui-pre-0.3.5/src/platform.rs` (`PlatformHeadlessRenderer`). These files are in Cargo's registry source for the exact lockfile version.

## Pixel stability

The test dispatcher has a default seed of zero and a simulated clock, but the screenshot path uses the real text system and a GPU renderer. Deterministic scheduling alone therefore does not establish bit-identical pixels. The local fixture produced identical pixels on repeated captures in one process. On macOS 26.6.2 (build 25G83) with an Apple M1 Max GPU (Metal 4), five screenshot probes run in separate fresh processes matched the committed baseline byte for byte: all six PNG files had SHA-256 `41a44c6e47c6e217a58fa770c999eeecd30f81cd6ef548cd4b179027d1123c0c`. Each probe used `MKIT_SCREENSHOT_PROBE_OUTPUT=/tmp/mkit-e11-runs/run-N.png cargo test -p mkit-harness --test screenshot --locked` with a distinct output path. Cross-machine pixel stability is **untested**. Hold visual baselines to a specified OS, renderer, font set, window size and scale; use an explicit image tolerance only after measuring its effect on real diffs. Do not mark Windows or Linux screenshot CI as passing until a headless renderer exists for them.

## Input and focus

The pinned crate has `TestAppContext::simulate_keystrokes` for space-separated parsed keystrokes, `simulate_input` for text, `dispatch_action`, and test-window mouse move/down/up/click methods. The simpler `TestAppWindow<V>` also exposes keystroke, text, and pointer simulation. `HeadlessAppContext` itself exposes `update_window` but no matching convenience `simulate_*` methods. A harness can dispatch keystrokes and pointer events through a test context or through `Window` using `update_window`. The E1 fixtures below verify these paths for their sample views.

`simulate_input` parses characters as keystrokes. It is not an IME composition API and does not exercise platform candidate selection, marked text, or a real input method. Japanese, Chinese, and Korean composition therefore needs a real-platform manual check unless an explicit test seam is built and verified.

For pointer scripts, the currently exposed test methods take pixel positions. The E1 script runner therefore needs a supplied center for each named target; the pinned test API does not provide a stable semantic target-to-bounds lookup. The `dispatches_scripted_pointer_and_keyboard_events_to_focused_gpui_view` fixture focuses a GPUI view and runs `click @target`, `press "enter ctrl-g"`, `type "hi"`, and `drag @a -> @b`. It observes a click, three key events, one dispatch of an action bound to `ctrl-g` in the `ScriptFixture` key context, and drag mouse down → move → up in order. A second fixture registers an `ElementInputHandler` backed by `EntityInputHandler`: `type "hello GPUI"` inserts that text, focus remains on the view, and `press "ctrl-g"` dispatches its bound action. The separate inspector integration test asserts entity state and changed screenshot pixels after input. None of these fixtures exercise native IME composition.

Sources: `gpui-pre-0.3.5/src/app/test_context.rs` (`dispatch_action`, `simulate_keystrokes`, `simulate_input`, `dispatch_keystroke` and mouse methods); `gpui-pre-0.3.5/src/app/test_app.rs` (test-window mouse methods); `gpui-pre-0.3.5/src/app/headless_app_context.rs` (public methods).

Upstream's [key dispatch guide at the pinned revision](https://github.com/zed-industries/zed/blob/d89e9c2124b2786a390c7a451c7488601b4da2e1/crates/gpui/docs/key_dispatch.md) describes binding actions in a `key_context`; its [testing example](https://github.com/zed-industries/zed/blob/d89e9c2124b2786a390c7a451c7488601b4da2e1/crates/gpui/examples/testing.rs) shows the intended test context pattern. The package source above controls exact `gpui-pre` API claims.

## Accessibility tree

`Window::debug_a11y_tree_json()` is public and returns the last captured AccessKit `TreeUpdate` as JSON through `window/a11y/debug.rs`. That serializer includes roles, semantic properties, actions, children and GPUI focus, plus frame metadata. Its `rendered_at`, `frame_number`, ephemeral node identifiers and debug provenance are unsuitable as-is for stable snapshots. The harness normalizes supplied debug JSON into stable semantic text with tree order, role, name, value, states, actions and focus. Unit and integration tests cover normalization and malformed tree handling; actual headless tree capture remains unavailable below.

The debug dump is optional: it is `None` until a tree update has been captured. The window starts with accessibility inactive, and tree construction during a frame is gated on activation via the platform adapter callback. `PlatformWindow` supplies a no-op `a11y_init` default, and the pinned `TestWindow` does not override it. A rendered GPUI `TestAppContext` window regression test confirms `is_a11y_active() == false`, `debug_a11y_tree_json() == None`, and `AccessibilitySnapshot::capture() == Err(Inactive)`. This is a source-backed blocker for the stock GPUI test platform, not a claim that all macOS windows lack accessibility. The real macOS platform installs an AccessKit adapter, but actual tree capture still depends on activation and has not been tested here. E1.4 needs a test-platform change or another explicit activation seam before it can snapshot the AccessKit tree headlessly.

Sources: `gpui-pre-0.3.5/src/window.rs` (`debug_a11y_tree_json`, accessibility initialization and render gating); `gpui-pre-0.3.5/src/window/a11y.rs` (`sync_active_flag`, `end_frame`, `debug_tree_json`); `gpui-pre-0.3.5/src/window/a11y/debug.rs` (`A11yDebug::to_json`); `gpui-pre-0.3.5/src/platform.rs` (`PlatformWindow::a11y_init` default); `gpui-pre-0.3.5/src/platform/test/window.rs` (`PlatformWindow` implementation).

## Local results and remaining checks

On macOS, `UPDATE_SNAPSHOTS=1 cargo test -p mkit-harness --test screenshot --locked` produced the baseline; subsequent `cargo test -p mkit-harness --test screenshot --locked` runs passed against it. `cargo test -p mkit-harness --lib --locked` passed seven unit tests, and the screenshot executable passed. The screenshot test uses a custom `harness = false` test target to run on the main thread; the default Rust test worker thread panicked with `Mac platform not created on main thread`. The fixture creates `HeadlessAppContext` with the current platform text system and Metal headless renderer, opens a hidden window, draws a frame, then calls `capture_screenshot`.

For a requested logical size of 180 × 60 at scale 1, the resulting PNG is 180 × 60. On this Retina host the backing test window was at native scale 2. Setting only `Window::set_scale_factor(1)` clipped the scene, so the harness now draws at native scale and resizes the capture to requested output dimensions. Repeated captures in the same process were pixel-identical. A requested 2× output was 360 × 120. The test asserts contrasting teal child pixels and more than eight bright pixels in the text area at both scales. The committed baseline has SHA-256 `41a44c6e47c6e217a58fa770c999eeecd30f81cd6ef548cd4b179027d1123c0c`; at 1× it contains 770 exact teal and 421 exact white pixels, plus antialiased glyph pixels.

Raw text probes initially produced no glyph pixels even though direct text shaping returned `Ok(1)`; setting Arial and refreshing before draw did not resolve this. Initializing `gpui_kit::base::init` in the screenshot fixture's `theme` callback made GPUI text paint. Removing that initialization reproduced zero glyph pixels. GPUI Kit is a test-only dev dependency for this fixture; `mkit-harness`'s runtime dependencies remain GPUI, its platform package, and `image`. This verifies text capture with that initialization on this Mac, but leaves the exact missing default setup and behavior on other hosts unresolved. The current rendered book examples initialize GPUI Kit in their screenshot fixtures.

The focused-view input fixture confirmed the action and pointer sequence above; its accessibility capture reported `Inactive`. The input-handler fixture verified text insertion, focus, key delivery, and action dispatch. `cargo test -p mkit-harness --lib --locked` passed all seven unit tests. IME composition was not exercised. `cargo test -p mkit-harness --test accessibility --locked` passed four integration tests: the real GPUI test-window inactive-accessibility regression plus three serializer tests covering semantic fields, volatile metadata removal, missing nodes, cycles, reused nodes, and invalid child shapes. The serializer tests supply JSON and do not prove live AccessKit capture. Per-state component conformance snapshots remain pending.

The four current rendered book example crates are `hello`, `counter`, `reactivity_views`, and `state_entities`. Each has a macOS harness screenshot test against a committed PNG in `book/src/images/`, and the book pages include code from the compiling crate and display the corresponding image. `contexts` is a nonvisual example with no window or screenshot. The baselines cover initial states at 640 × 400 and scale 1.0, not every interaction, theme, or scale. Screenshot coverage must expand as more rendered examples are added.

`cargo test -p mkit-inspector --locked` passed on macOS: three protocol unit tests and the `harness = false` MCP fixture executable (which runs assertions from `main`, so Cargo reports zero named tests for that target). MCP `launch` starts any current rendered book example (`hello`, `counter`, `state_entities`, or `reactivity_views`) or the gallery's shared preview view in one headless window per process. The nonvisual `contexts` example returns an explicit error. `apps/gallery/src/main.rs` opens the same gallery view; `cargo check -p mkit-gallery --locked` passed. The fixture test checks `hello` input, click, state, and changed screenshot pixels; gallery launch, click, state, and screenshot; `counter` click, state, and changed screenshot pixels; `state_entities` strong and weak button clicks, state, and screenshot; and `reactivity_views` click, observer/event state, and screenshot. These are actual example views in persistent headless sessions, with narrow read-only state accessors. `a11y_tree` still reports an MCP error stating that accessibility is inactive. Named click targets are limited to those exercised by the fixtures, with numeric coordinates also accepted. More book examples and gallery component states must gain inspector coverage as they are implemented. The supplied renderer makes headless launch unsupported outside macOS. No E3 book evaluation has used the inspector yet.

Windows, Linux, another macOS machine, and cross-machine pixel comparisons have not been run. The provided renderer remains macOS-only by source inspection.
